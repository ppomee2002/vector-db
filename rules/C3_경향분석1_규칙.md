## 블록 모델
- 블록 번호 = pk // R. doc 배치 pk = chunk_id, rand 배치 pk = np.random.default_rng(1).permutation(N)[chunk_id], N = 1,000,000 (README "100만", c1_milvus.py pk_maps).
- R(블록 하나의 행 수): 지현 cold doc top10(one, query) 쿼리별 miss_bytes 평균 = 4MiB × 예측 고유 블록 수 평균이 되도록 고른다(보정).
- 검증: 같은 R로 doc all1, rand top10, rand all1의 평균 miss_bytes를 예측해 실제와 비교. 세 개 모두 오차 ≤ 25%면 블록 모델을 쓴다. 하나라도 넘으면 블록 단위 결과는 "모델 불일치"로 표시하고 판정에 쓰지 않는다(chunk·문서 단위만 기술).
- 민감도: R/2, 2R로도 계산해 함께 보고. 판정은 R 기준.

## A. 질의별 Fetch 비용 편차 → 비용 기반 스케줄링 검토 여부
- 대상: cold doc 배치, 한 번에 요청(one, query), read_set bc1 (파이프라인과 같은 이웃 규칙).
- A1: Fetch 지연(lat_ms)의 변동계수 CV = 표준편차/평균 ≥ 0.5
- A2: 실행 전에 알 수 있는 값(예측 고유 블록 수, 블록 모델이 검증을 통과한 경우만)과 lat_ms의 Spearman ≥ 0.5
- A1·A2 모두 만족 → "비용 편차 있음, 예측 가능 → 비용 기반 스케줄링 검토할 만함". A1만 → "편차는 있으나 실행 전 예측 어려움". A1 불만족 → "편차 작음".
- warm(c_serial fetch_ms)도 A1만 같은 기준으로 따로 보고.
- 이유: CV 0.5 = 표준편차가 평균의 절반. 그보다 작으면 순서를 바꿔도 기다리는 시간 차이가 작다고 봄. Spearman 0.5는 흔히 '중간 정도' 상관으로 부르는 값. 둘 다 근거 약함.

## B. 동시 질의 간 블록 중복 → 읽기 병합·공동 스케줄링 검토 여부
- 동시 집합 근사: 도착 순서에서 연속 16개(동시 16). 질의별 시작·끝 시각이 결과에 없어 근사.
- B1(기술): 창 안 중복률 D = 1 − (창의 고유 블록 수) / (질의별 고유 블록 수의 합). doc·rand × top10·all1. chunk·문서 단위 중복도 같이 적는다.
- B2(판정): 캐시가 작을 때 순서를 묶으면 블록 읽기가 줄어드는가. LRU 캐시 모의(용량 = 전체 블록의 25%, 50%)
  - 도착 순서 그대로 vs 앞에서부터 64개(동시 16의 4배)씩 모아 그 안에서 블록이 겹치는 질의끼리 붙여 다시 정렬(욕심 방식: 앞 질의와 겹치는 블록이 가장 많은 질의를 다음으로).
  - doc 배치 all1에서 두 용량 모두 블록 읽기(miss) 감소 ≥ 10% → "공동 스케줄링 검토할 만함". 아니면 "효과 작음".
  - 이유: 팀 C1 목표가 물리 I/O 30% 감소. 그 1/3 미만이면 스케줄러 복잡도에 비해 작다고 봄. 64·25%·50%는 근거 없음.
- Milvus 캐시 교체 방식이 LRU인지는 확인하지 않았다. 같은 블록을 동시에 읽을 때 Milvus가 한 번만 읽는지도 미확인.
