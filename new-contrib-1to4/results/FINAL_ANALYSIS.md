- 작성일: 2026-11-16
- 근거: `/workspace/jaeeun/sel_fetch/` 아래 저장된 결과 파일(CSV, JSON)과 로그만 사용. 이 문서를 쓰면서 새 실험이나 새 계산은 하지 않았다. 판단 요약의 수치를 확인하려고 파일 값끼리 나눈 비율(예: 0.9894 → 98.9%, dup_total / na_bytes_total)만 계산했고, 그런 값에는 "(파일 값으로 계산)"이라고 표시했다.

## 2. ③ Selective Context Fetch

### 질문
1. ANN Top-10과 리랭킹 후 최종 Top-10은 얼마나 다른가?
2. 리랭킹 전에 싼 정보로 최종 Top-10에 들 후보를 미리 골라, 본문 Fetch를 줄일 수 있는가?

### 설정
- 실제 쿼리 3,452개의 ANN Top-100(ef=256)을 cross-encoder로 리랭킹했다.
- 최종 Top-10을 정답(y=1)으로 놓고 다음 모델들을 쿼리 단위 out-of-fold로 학습했다.
  - M0: ANN 정보만 사용
  - M0+DOC: 문서 구조 특징 추가
  - M0+EMB: 후보 간 임베딩 관계 특징 추가
  - M1: 위 특징 모두 사용
  - M1-noPos: M1에서 위치 특징 제외
  - M0+POS: M0에 위치 특징만 추가
- 같은 Fetch 예산(B개)에서 보존율(최종 Top-10 중 Fetch한 비율), 10위 밖 승격 후보 회수율, nDCG@10을 비교했다.
- I/O 측정 조건: 저장 방식은 기존 chunk 순서 그대로, chunk별 개별 pread, 단일 스레드, 매 실행 전 콜드 캐시, 장치는 loop1 (`logs/io_check.log`)

### 판단 (판단 요약)
- **가능성 확인 (효과 중간 크기).**
- 질문 ①: Overlap@10 평균은 약 5/10이고, 최종 Top-10의 약 49%가 ANN 10위 밖에서 왔다. 리랭킹으로 nDCG@10이 오른다. 따라서 의미 있는 차이가 있다.
- Top-K 축소만으로도 20~30개를 Fetch하면 nDCG가 전체의 99% 수준이다. 그래서 "100개를 다 읽지 말자"는 Top-K로 이미 얻는 효과이고 기여가 아니다.
- 질문 ②
  - ANN 정보만 쓴 M0는 Top-K와 거의 같다(M0 ≈ Top-K).
  - 문서 구조와 후보 간 관계 특징을 더한 모델은 위치 특징을 빼도(M1-noPos) 같은 예산에서 보존율이 +2~3%p 높고, 10위 밖 승격 후보 회수율도 오른다.
- 위치 편향: 정답 chunk가 문서 첫 chunk와 corpus 앞쪽에 몰려 있음을 확인했다. 그래서 위치 특징을 뺀 모델로 판정한다.
- I/O
  - 같은 품질에서 Fetch는 약 7%, 디스크 읽기 횟수는 약 8.5% 줄었다.
  - latency는 실행 순서 고정과 공유 디스크 잡음 때문에 판단을 보류한다. 재측정은 하지 않았다.
  - 선별 비용(쿼리당 1ms 미만)이 로컬 Fetch 절감보다 크다. 따라서 Fetch 비용이 큰 저장 환경(원격·콜드 저장소)에서만 유효한 조건부 효과다.
- nDCG가 전체 리랭킹보다 약간 높게 나온 것(M1 예산 20: 0.4647 > 0.4539)은 품질 향상이 아니라 앙상블 효과로 본다. 그래서 "품질 손실 없이 Fetch 감소"로만 주장한다.
- Qdrant 교차 검증은 저장 공간 부족(WAL)으로 하지 못했다.

### 한계
- 리랭커 1종(ms-marco-MiniLM-L-6-v2), 데이터셋 1종(NQ), Milvus HNSW 1종으로만 측정했다.
- latency는 1회 고정 순서 실행에서 공유 loop 장치로 측정해서 판단할 수 없다.
- Qdrant 교차 검증을 하지 못했다.
- 선행 기준선(Adaptive-k 등)과 직접 비교하지 않았다.

## 3. ② Semantic Approximate Reuse

### 질문
이전 쿼리의 Context로 캐시에 들어온 chunk 가운데 의미적으로 비슷한 chunk(유사도 ≥ τ)를, 지금 요청된 chunk 대신 재사용하면 캐시 hit가 의미 있게 늘어나는가? 그렇게 바꿔 써도 사실관계가 유지되는가?

### 설정
- 실제 쿼리 3,452개를 썼다. 요청은 쿼리마다 최종 Top-10으로, 총 34,520건이고 서로 다른 chunk는 32,715개다. 요청 본문은 12.90MB다 (`logs/reuse_full.log`).
- 캐시: 이전 쿼리의 chunk만 보관한다. 대체할 chunk는 현재 쿼리의 요청 집합에 없어야 한다 (`results/reuse_full/reuse_config.json`).
- 캐시 크기와 접근 흐름
  - 캐시 크기: M2 비교용 5%(Context만 / 전체를 Context로 환산), 요청 집합의 5% / 25% / 100%
  - 접근 흐름: distinct(판정용), natural(M2), zipf 1.2, zipf 0.9
- 계산 방식: 본문만 저장하는 경우(text_only)와 임베딩도 저장하는 경우(text+emb, chunk당 1,536B)를 따로 계산했다.
- 사실관계: NLI 모델 `cross-encoder/nli-deberta-v3-small`, NQ-open 정답 매칭률 0.653 (`logs/reuse_full.log`)

## 4. ① Document-based Range Read (핵심 보류 + 축소판)

### 질문
chunk를 겹치게 자르는 RAG에서 두 방식의 저장 바이트와 논리적 읽기 바이트가 어떻게 다른가?
- (나): 원문을 저장하고 offset·length로 필요한 구간의 합집합만 읽는 방식
- (가): chunk를 개별 저장하고 연속 chunk를 묶어 읽는 방식 (김지현 님 방식)

### 핵심 보류 근거 (판단 요약)
- 김지현 님 실험 2(문서 순 배치 + 묶음 읽기)가 ①의 Range Read와 같은 구조로 이미 측정됐다. 읽기 횟수 24.1 → 5.7, KB 108.6 → 37.5, p50 1966 → 475µs였다. M4 이상적 연속 배치와도 겹친다.
- 이 수치는 이 폴더의 결과 파일로는 확인할 수 없다. 근거 파일로 지정된 `results/q1_rangeread_hold.md`가 없다. [확인 필요] 참조.

### 축소판 설정 (`scripts/q1_overlap.py`, `results/q1_overlap/config.json`)
- 텍스트 바이트만 계산했다. 디스크 읽기, latency 측정, Milvus, GPU는 쓰지 않았다.
- 원문 복원: 문서별로 chunk를 chunk_idx 순서로 이었다.
- 재분할: 창 64단어, 겹침 0단어(0%, 원래 경계 그대로) / 6단어(10%) / 13단어(20%). 마지막 조각이 32단어 미만이면 앞 조각에 붙였다.
- 필요 구간: 최종 Context chunk의 원래 단어 구간. 확장은 ±0과 ±1(같은 문서 안의 앞뒤 원래 chunk)이다.
- 바이트 모델: UTF-8, 단어 사이 공백 1바이트.
- 차이 분해: (가) − (나) = 중복 + 경계 초과 − 경계 공백
- 4KB 페이지: 연속 읽기 1회마다 ceil(바이트 / 4096)을 더한 이상적 값이다.
- 대상: 실제 쿼리 3,452개, train 표본 2,000개(④에서 리랭킹한 표본).

### 판단 (판단 요약)
- **핵심은 보류, 축소판은 조건부 효과.**
- 축소판: 검증 V1~V4 위반은 0이다. 겹침 0%에서는 두 방식의 차이가 단어 사이 경계 공백뿐이다(중복·초과 0). 따라서 겹침이 없으면 묶음 읽기 대비 추가 절감이 없음을 확인했다.
- 겹침 10%·20%
  - 저장 바이트는 약 +10%와 +25%다.
  - 논리적 읽기 증가분의 대부분은 "경계 초과"다. 이는 "필요 구간을 원래 chunk 경계로 고정"한 설계 가정에서 생긴 것이라 기여로 주장하지 않는다.
  - 주장할 수 있는 것은 "중복" 부분뿐이다(겹침 10%에서 약 10%, 20%에서 약 25~28%).
  - 읽기 횟수는 줄지 않는다. 파일 값으로는 (나)의 읽기 횟수가 (가)보다 같거나 많다.
- 이 결과는 본문 텍스트 바이트만 센 이상적 모델이다. 겹침 0%에서 두 방식이 같은 것은 chunk별 메타데이터·키·레코드 헤더 같은 저장 오버헤드가 없다고 가정했을 때만 성립한다. 실제 SSD I/O나 latency 개선을 뜻하지 않는다.

### 한계
- 실제 저장 포맷의 오버헤드(메타데이터, 키, 레코드 헤더)를 반영하지 않았다.
- 실제 SSD I/O, latency, 고지연 저장소(S3 range GET)는 검증하지 않았다.
- 필요 구간을 원래 chunk 경계로 고정했다.
- 보류 근거인 김지현 님 수치는 이 폴더의 파일로 확인하지 못했다.

## 5. ④ Index-guided Data Placement (전체 실행 + 재분석)

### 질문
쿼리 로그 없이 벡터 인덱스 구조만으로 자주 접근될 chunk를 예측할 수 있는가? 여기서 인덱스 구조 신호는 k-occurrence(hubness)다. 배치를 실제로 바꿔 I/O를 재는 실험은 하지 않았다.

### 설정 (`results/q4_full/config.json`, `logs/q4_full.log`, `logs/embed_train_minilm.log`)
- **예측값 (로그 없음):** 100만 chunk 각각을 쿼리로 Milvus에서 26개를 검색하고, 같은 ID만 뺀 뒤 k=10(주)과 k=25(보조) 안에 등장한 횟수를 셌다. ef=64, 전체 100만 모드.
- **train 쿼리**
  - 김지현 님 `train_queries.jsonl`의 텍스트를 공통 데이터와 같은 MiniLM 설정(max_seq_length 128, fp16, normalize)으로 다시 임베딩했다. 김지현 님 임베딩은 bge-small-en-v1.5라서 쓰지 않았다.
  - 검증 코사인은 [1.0, 0.999999, 1.0]이다 (`data/q_train_minilm_verify.json`, `logs/embed_train_minilm.log`).
  - 원본 132,803개, 텍스트 기준 중복 제거 후 132,803개(중복 0건)를 seed 0으로 나눴다. 로그 절반 66,401개, 평가 절반 66,402개다.
- **정답**
  - 평가 쿼리의 ANN Top-10 접근 빈도 (ef=64)
  - 평가 쿼리 2,000개 표본의 리랭킹 최종 Top-10 (Top-100은 ef=256)
  - 실제 쿼리 3,452개의 ANN Top-10과 최종 Context (기존 CSV)
- **비교 대상:** 로그 기반(로그 절반의 접근 빈도), 무작위(seed 10개 평균), 오라클, 첫 chunk, 문서 길이. 점수가 같으면 고정 seed로 무작위 순서를 정했다.
- **지표:** 상위 1/5/10% 포함률(chunk 수 기준, 바이트 기준), 회복률 = (예측 − 무작위) / (로그 − 무작위), 쿼리를 재표집하는 bootstrap 1,000회 95% 신뢰구간

- **부분적 예측력, 단독 기여로는 보류.**

  - 로그 기반 대비 회복률은 약 18%(1%), 30%(5%), 38%(10%)이고, 신뢰구간이 0과 멀리 떨어져 있다.
- 실제 Context(리랭킹 후) 기준
  - 회복률이 낮아지고, "문서 첫 chunk" 단순 규칙이 상위 1~5%에서 더 높다.
  - ±1 확장에서도 1%와 5%는 첫 chunk가, 10%만 k-occ가 약간 우세하다.
  - 예산에 따라 결론이 달라서 "중간"으로 본다.
  - 상위 10% 우세의 paired bootstrap 신뢰구간: train 표본 ±1 포함률 차이 0.0114 [0.0064, 0.0166], 실제 ±1 0.0069 [0.0028, 0.0112] (파일 값)
- 문서 앞쪽(d0~d1)을 빼거나 10분위별로 봐도 결론이 같다. 따라서 편향 때문이 아니다. 앞쪽 제외에서 일부 칸이 달라진 점은 [확인 필요] 참조.
- train 쿼리는 김지현 님 bge 임베딩이 아니라 공통 데이터와 같은 MiniLM으로 다시 임베딩했다(검증 코사인 ≈ 1.0).

### 한계
- 배치를 실제로 바꾸지 않았고 I/O도 측정하지 않았다.
- 정답이 표본(2,000개, 3,452개)이면 접근이 희소하다(접근 chunk가 전체의 1.9~3.3%). 그래서 Hot 5% 집합에 접근 0회인 chunk가 무작위 동점 처리로 들어간다 (`hot_classification.csv`의 hot_min_count).

- 데이터셋 1종, 임베딩 1종, HNSW ef=64로만 측정했다.

## 6. 선행 연구와의 관계

> 아래 내용은 연구자가 정리한 선행 연구 조사를 그대로 옮긴 것이다. 논문은 요약·초록 수준으로만 확인했다. 2025~2026년 preprint는 동료 심사 여부를 확인하지 않았다. 이 문서를 쓰면서 추가 검색은 하지 않았다.

### ③과 겹칠 가능성
"비싼 단계 전에 싼 정보로 후보를 미리 골라내기"는 정보검색에서 오래된 연구 흐름이다. ③의 결과가 잘 나온 것은 효과가 알려진 기법 계열이기 때문일 수 있다.
- **Cascade ranking:** Wang, Lin, Metzler, SIGIR 2011 / Cost-aware cascade ranking, SIGIR 2017. 단계마다 더 비싼 랭커를 더 적은 후보에 적용한다.
- **리랭커 early exit·사전 필터:** Busolin et al., SIGIR 2025(cross-encoder 앞단 필터) / LEAR(top-k에 못 들 문서를 미리 예측). ③의 "최종 Top-10 소속을 미리 예측"과 거의 같은 발상이다.
- **Ranked list truncation:** Choppy(SIGIR 2020), AttnCut(AAAI 2021). ③의 "몇 개 읽을지" 부분과 겹친다.
- **RAG 적응형 k:** Adaptive-k(2025, 점수 분포로 개수 결정), DynamicRAG(NeurIPS 2025), Context-Picker(2025). ③의 "M0 ≈ Top-K" 결과와 같은 계열이다.
- **Late materialization (DB 기법, VLDB 2025 SLM 등):** 순위를 확정한 뒤 최종 결과의 본문만 읽는다. ③의 시스템적 근거와 같은 계열이다.
- **③이 주장할 수 있는 차별점**
  1. 최적화 대상이 리랭커 계산이 아니라 저장소에서 본문을 읽는 Context Fetch I/O다.
  2. 문서 구조 신호(같은 문서 적중, 인접 chunk)가 예측에 가장 크게 기여하고, 위치 편향을 빼도 유지된다.
  3. 선별 비용과 Fetch 비용의 손익분기 조건을 제시한다.
  - 이 세 가지 외에는 새로움을 주장하지 않는다.
  - 선행 기준선(예: Adaptive-k)과의 직접 비교는 아직 하지 않았다.

### ④와 겹칠 가능성
- 허브 이론은 Radovanović et al., JMLR 2010이다.
- "Cache Mechanism for Agent RAG Systems"(arXiv 2511.02919)는 허브 점수와 쿼리 빈도를 섞어 캐시 우선순위를 정한다. 따라서 허브 기반 예측 자체는 새롭지 않다.
- ④의 결과(실제 Context 기준에서 첫 chunk 규칙보다 약함)는 이 아이디어의 한계를 보여 주는 근거로 쓸 수 있다.

### 시스템 계열
- CaGR-RAG(arXiv 2505.01164)와 CALL(HiPC 2025)은 쿼리 접근 패턴을 기반으로 그룹화·프리페치한다. ConStore와 같은 로그·패턴 기반 계열이다.
- Turbocharging Vector Databases using Modern SSDs(VLDB 2025)는 배치와 지역성을 개선한다. 김지현 님 Layout, M4와 겹친다.

### ① 관련
원문과 위치를 저장한 뒤 필요한 부분만 읽는 것은 late materialization과 같은 계열의 실무 기법이다. 그래서 연구 기여가 아니라 "겹침 비용의 정량화"로만 기술한다.

### ② 관련
MMR과 근사 중복 선택 연구는 주로 한 쿼리 안의 중복을 다룬다. ②(쿼리 사이 근사 재사용)는 탈락이라 영향이 없다.
