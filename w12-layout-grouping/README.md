# W12: 문서 순 배치와 이웃 묶어 읽기 vs ConStore (파일, Qdrant, Milvus)

RAG가 이웃 chunk까지 읽을 때(±1), chunk를 **문서 순서대로** 배치하면 **ConStore 방식**(쿼리 로그 기반 배치)보다 읽는 양이 40~53% 적어요. 파일, Qdrant, Milvus 세 환경에서 모두 같았어요.
반대로 **반복되는 쿼리(본 쿼리)에서 top-k만 읽으면** ConStore 방식이 가장 적게 읽어요. 처음 보는 쿼리에서는 둘이 비슷해요.

지난주 `m4-data-layout`(모티베이션 실험)에 이어지는 실험이에요. Qdrant와 Milvus 실험은 그 브랜치의 스크립트(`common.py`, `measure.py`, `qdrant_ctl.sh`, `milvus_common.py`)를 그대로 불러 써요.

## 실험 환경
| | 파일 | Qdrant | Milvus |
|---|---|---|---|
| 데이터 | BEIR NQ 2,681,468 passage (위키 문서 108,593개, 문단 순서 검증함) | 지난주 NQ 부분집합 150,002 chunk | Qdrant와 같음 |
| 임베딩 | bge-small-en-v1.5 (Recall@10 74.2%) | all-MiniLM-L6-v2 | 같음 |
| 읽기 방식 | 배치별로 원문을 파일 하나에 저장, 4KB `O_DIRECT` 읽기, 붙은 블록은 한 번에 읽음 | Qdrant 1.20.0, `on_disk_payload`, 세그먼트 1개·1개씩 적재 (넣은 순서 유지) | Milvus 2.6.23, PK = 배치 순서 (Milvus는 PK 순서로 저장) |
| 지표 | 쿼리당 read 횟수·바이트·지연, `/proc/diskstats`와 앱 집계 대조 (비율 1.000) | 쿼리당 새로 읽힌 데이터 페이지 수 (`mincore`), 쿼리마다 cold | 쿼리당 저장소에서 읽은 바이트, 쿼리마다 release/load |
| 쿼리 | 본 쿼리 1,000개 (로그 안) / 처음 보는 쿼리 1,000개 (NQ test) | 본 쿼리 500 (train) / 처음 보는 쿼리 500 (test) | 각 앞 100개 |

ConStore 방식의 로그: NQ train 쿼리(3만 개 또는 전체 132,803개)의 top-10. 모든 배치에 같은 top-k, 같은 이웃, 같은 읽기 방식을 적용했어요.

## 배치
`R`/`rand` 랜덤 · `D`/`doc` 문서 ID + chunk 순서 (**우리 방식**, 로그 없음) · `K` 임베딩 k-means · `L` 단순 로그 묶음 ·
`P64` ConStore 방식 (공동 검색 그래프 → METIS 분할, 그룹당 약 64개, 그룹 안 정렬, 로그에 없는 문서는 k-means) · `P64x` 로그 전체를 쓴 ConStore 방식 ·
`HC` ConStore의 로그 영역 + 나머지 문서 순 · `HN` 이웃 포함 ConStore 로그 영역 + 나머지 문서 순

## 핵심 결과
- 이웃(±1)까지 읽으면 문서 순이 ConStore 방식보다 Qdrant에서 페이지 40~47%, Milvus에서 바이트 43~53%를 적게 읽어요. 파일 실험에서도 k=80까지 같아요.
- 문서 순은 로그도 임베딩도 필요 없고, 임베딩 k-means보다 약 20% 빨라요(파일). ConStore 논문은 문서 순과 비교하지 않았어요.
- 반복 쿼리에서 top-k만 읽으면 ConStore 방식이 이겨요(Qdrant 3.05 대 5.27 페이지, Milvus 4.8 대 10.2MB). 처음 보는 쿼리 ±0에서는 둘의 차이가 약 10% 안이고, 어느 쪽이 나은지는 로그 크기에 따라 달라요.
- 문서 순에서 ±1 이웃을 붙이면 I/O가 거의 늘지 않는데 정답 포함률은 5~6%p 올라요. 정답 포함률 약 79.5%를 얻는 데 D(top-10 ±1)는 read 5.66회, P64(top-15)는 8.11회예요.
- 하이브리드(HN)는 본 쿼리 ±1에서 가장 좋지만, 처음 보는 쿼리 ±1에서는 문서 순보다 나빠요.

## 한계
- ConStore는 논문을 보고 재현했어요. 그룹 크기(64)는 논문에 값이 없어 우리가 정했고, 로그 간선은 top-10을 썼어요(top-20 가중치 버전도 결과가 같았어요).
- 15만 chunk 부분집합에서는 NQ train 쿼리 대부분의 정답이 코퍼스 밖이라, 큰 로그의 질이 파일 실험보다 떨어져요.
- 단일 스레드 쿼리당 비용이고 QPS는 아니에요. 데이터셋은 NQ 하나예요. Qdrant의 세그먼트 1개·1개씩 적재는 배치 효과를 보기 위한 실험용 설정이에요. Milvus의 읽은 바이트는 서버 전체 지표예요(다른 사용자가 없는 새벽에 측정).
- 이웃 쓸모(정답 포함률)는 268만 개 파일 실험에서만 계산했어요.
