# W13 C1: 문서 순 저장소 + 이웃 묶어 읽기 (파일, Milvus)

김지현 (C1 담당)

이번 주 공통 데이터(NQ 100만 chunk)에서 chunk를 **문서 순서대로** 저장하면, top-10에 이웃을 붙여도 읽는 비용이 거의 늘지 않아요.
±1 이웃을 전부 붙였을 때 무작위 배치보다 **읽는 양이 파일에서 66%, Milvus에서 75% 줄고 지연은 각각 3.9배, 2.4배 짧아져요.**
단, 이 효과는 저장소에서 실제로 읽을 때(파일 O_DIRECT, Milvus 콜드)만 나타나요. 캐시에 다 올라간 웜 상태의 Milvus에서는 배치 차이가 없어요.

W12(`w12-layout-grouping`)에서 확인한 결과를 이번 주 파이프라인 공통 데이터로 다시 잰 실험이에요.

## 실험 환경
| | 파일 저장소 | Milvus |
|---|---|---|
| 데이터 | NQ 100만 chunk (64단어, 문서 27,133개). `/workspace/junlim/data_nq/chunks.jsonl`을 읽기만 함. chunk_id = 줄 번호 = `nq_seq`·`nq1m_sel`의 pk | 같음 |
| 배치 | `doc`: 줄 번호 순서 (= 문서 번호, 문서 안 순서). `rand`: 무작위 (seed 1) | `jihyeon/w13c1_doc` (pk = 줄 번호), `jihyeon/w13c1_rand` (pk 무작위, seed 1). 둘 다 pk 순서로 넣음 |
| 읽기 | 본문을 이어 붙인 파일, 4KB `O_DIRECT`, 단일 스레드. 개별 = chunk마다 pread, 묶어 읽기 = 붙은 블록을 pread 한 번 | Milvus 2.6.23, pymilvus 3.0.3, `get(ids)`. 한 번에 = 요청 1번, 따로 = top-10 요청 후 이웃 요청, chunk마다 = chunk 수만큼 요청 |
| 캐시 조건 | O_DIRECT라 매번 디스크에서 읽음 | 콜드(M1): 조회마다 release/load, `warmup.scalarField=disable`. 웜(M2): 한 번 load, 예열 후 측정 |
| 지표 | 쿼리당 read 횟수·바이트·지연. `/proc/diskstats`와 대조 (비율 1.000) | 쿼리당 저장소에서 읽은 바이트 (`internal_cache_cell_access_miss_bytes_total` 전후 차이), 지연 |
| 쿼리 | NQ test 3,452개, 3회 반복 | 콜드 100개 (같은 쿼리끼리 짝지어 비교), 웜 500개 × 3회 |
| 측정 전 상태 | 장치 읽기 0회/초 | Milvus 요청 0건/초 (측정 전후 모두) |

읽을 chunk 목록은 이재은의 ANN·Rerank 결과(`ann_top100_real.csv`, `rerank_top100_real.csv`)에서 만들었고, 이웃은 임준의 C2 규칙(`pf3_rules.py`)을 그대로 썼어요.
- top-10: Rerank 후 최종 10개
- B+C1 이웃: top-10 + C2 규칙 B+C1로 고른 이웃
- ±1 전부: top-10 + 모든 결과의 앞뒤 chunk
- ANN 후보 30 / 100: Rerank 전 후보

Milvus 컬렉션의 벡터는 8차원 가짜 벡터(FLAT)예요. 검색은 하지 않고 본문 조회만 재요.

## 결과

**읽는 범위와 정답 포함률** (정답 문단 qrels 기준, 쿼리 3,452개)
| 읽는 범위 | 쿼리당 chunk | 정답 포함률 |
|---|---|---|
| top-10 | 10.0 | 80.4% |
| top-10 + B+C1 이웃 | 18.2 | 84.4% |
| top-10 ±1 전부 | 24.7 | 84.7% |
| ANN 후보 30 | 30.0 | 85.2% |
| ANN 후보 100 | 100.0 | 91.7% |

**파일 저장소 (E1): 쿼리당 read 횟수 / 지연 p50**
| 읽는 범위 | rand 개별 | doc 묶어 읽기 | doc ÷ rand (횟수) |
|---|---|---|---|
| top-10 | 10.0회 / 781us | 6.21회 / 506us | 0.62 |
| + B+C1 이웃 | 18.2회 / 1,450us | 6.13회 / 501us | 0.34 |
| ±1 전부 | 24.7회 / 2,002us | **6.13회 / 510us** | **0.25** |

- doc + 묶어 읽기에서는 이웃을 붙여도 read 횟수(6.21 → 6.13)와 지연(506 → 510us)이 그대로예요. 읽는 양만 32.6KB → 36.9KB(+13%) 늘어요.
- 배치만 바꾸거나(doc 개별) 묶어 읽기만 켜면(rand 묶어 읽기) rand 개별과 같아요. 둘 다 있어야 효과가 나요.
- 병합 간격(E2): gap을 64KB까지 늘리면 read 6.13 → 5.47회(−11%), 지연 510 → 448us(−12%), 읽는 양 +21%. 효과가 작아서 gap 0으로 충분해요.
- Rerank 전 후보(E3): ANN 후보 100개를 읽을 때 read 100 → 52.8회, p50 7.9 → 4.2ms. 후보 30개도 0.55배예요.

**Milvus 콜드 (M1): 쿼리당 저장소에서 읽은 양 / 지연 p50** (쿼리 100개, 한 번에 요청)
| 읽는 범위 | rand | doc | doc ÷ rand 읽은 양 [95% 구간] | doc ÷ rand 지연 [95% 구간] |
|---|---|---|---|---|
| top-10 | 40.2MB / 102ms | 23.7MB / 80ms | 0.59 [0.54~0.64] | 0.79 [0.76~0.82] |
| + B+C1 이웃 | 70.6MB / 147ms | 23.7MB / 82ms | 0.34 [0.30~0.37] | 0.56 [0.52~0.60] |
| ±1 전부 | 95.4MB / 199ms | **23.7MB / 83ms** | **0.25 [0.23~0.27]** | **0.42 [0.40~0.44]** |
| ANN 후보 30 | 110MB / 226ms | 56.2MB / 118ms | 0.51 [0.47~0.55] | 0.57 [0.53~0.61] |
| ANN 후보 100 | 264MB / 519ms | 153MB / 315ms | 0.58 [0.54~0.62] | 0.58 [0.54~0.62] |

- Milvus는 본문을 4MiB 단위로 읽어요(2만 행 점검에서 확인). doc 배치에서는 이웃이 같은 4MiB 안에 있어서, 이웃을 다 붙여도 읽는 양이 23.7MB 그대로예요.
- 결과와 이웃을 따로 요청하면 읽는 양은 같고 지연만 7~23% 늘어요. 한 번에 요청하는 게 나아요.

**Milvus 웜 (M2): 지연 p50** (쿼리 500개 × 3회, 저장소 읽기 0MB)
| 읽는 범위 | 한 번에 (rand / doc) | chunk마다 따로 (rand / doc) |
|---|---|---|
| top-10 | 5.04 / 4.98ms | 47.8 / 47.4ms |
| + B+C1 이웃 | 5.20 / 5.25ms | 85.2 / 85.7ms |
| ±1 전부 | 5.39 / 5.24ms | 119.7 / 119.6ms |
| ANN 후보 100 | 7.00 / 6.77ms | 474.2 / 471.2ms |

- 캐시에 다 올라간 뒤에는 요청 수가 지연을 정해요. 한 번에 요청하면 범위와 상관없이 5~7ms이고, chunk마다 요청하면 요청 하나에 약 4.7ms씩 늘어요.
- 웜에서는 doc과 rand 차이가 없어요. 배치 효과는 저장소를 실제로 읽는 조건에서만 나타나요.

## 한계
- 모두 단일 스레드, 쿼리 하나씩 읽었어요. 동시 요청에서의 효과는 C3와 합쳐서 봐야 해요.
- Milvus 콜드는 조회마다 release/load를 해서 동시 실행과 같이 잴 수 없어요.
- Milvus 읽은 양은 서버 전체 메트릭이라, 다른 사람이 Milvus를 안 쓰는 시간(측정 전후 요청 0건 확인)에 쟀어요.
- `w13c1_*`는 `warmup.scalarField=disable`, mmap 없이 캐시로 읽어요. 본문을 mmap으로 읽는 `nq_seq`와 조회 경로가 달라요.
- 파일 저장소는 Milvus 밖이에요. 공유 장치(loop1)라 지연보다 read 횟수·바이트를 주 지표로 봐요.
