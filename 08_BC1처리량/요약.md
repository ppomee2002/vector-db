# 08 규칙 B+C1(BC1) 처리량 측정 (11/17 01:45~02:12 KST)

서버 cap-vdb, Milvus 2.6.23, nq_seq(100만 Chunk, 64단어), 평소 상태(캐시 따뜻함, 디스크 읽기 모든 구간 0). 측정 중 다른 계정의 새 프로세스 없음, 오류 0.
목적: 정답 포함률이 규칙 B보다 높은 BC1(B + 1위 Chunk의 이웃)의 처리량이 11/16 측정에 없어서 잰다.
코드: bench_pf4.py(f8f14293, bench_pf3.py + 정책 rBC1, 다른 정책 동작 동일), run_bc1.sh(43dd8bcb), run_bc1b.sh(1c412d33). 11/16 결과(pf3_out)와 bench_pf3.py는 건드리지 않음.
조건은 11/16 pf3 load와 같다: 동시 요청 64, 요청 상한 8, 예열 5초 + 측정 20초, 측정 전 실제 질문 3,452개의 결과와 이웃 전부를 한 번 읽어 캐시를 데움.

## 2차 (run_bc1b.sh, 02:02~02:12, 결과 bc1b_results_1116_1712.tgz)
판단 기준(측정 전에 정함): 부하 측정 4회 모두 rBC1이 rB보다 낮으면 B 유지, 아니면(범위가 겹치면) BC1으로 교체.

### 요청을 하나씩 (seq, 같은 질문으로 정책 9개를 번갈아, 400질문 × 3회, 짝지은 차이와 95% 구간)
| 비교 | 평균 차이 (ms) |
|---|---|
| rBC1 − rB | −0.10 ± 0.18 |
| rBC1 − none | +0.03 ± 0.22 |
| rB − none | +0.13 ± 0.28 |
| all − none | +0.41 ± 0.33 |
요청 하나의 지연은 정책 간에 거의 같다(평균 11.0~11.5ms). 이웃 전부만 0.4ms 정도 길다.

### 부하 (load, 4회, 4×4 균형 순서: 각 정책이 모든 자리와 모든 앞 정책을 한 번씩 가짐)
| 정책 | QPS 평균 [최소–최대] | p99 평균 [최소–최대] | 요청당 읽은 Chunk |
|---|---|---|---|
| none (top-10만) | 663 [624–710] | 183 [151–203] | 9.95 |
| rBC1 (규칙 B+C1) | 650 [598–699] | 181 [165–202] | 18.6 |
| all (이웃 전부) | 645 [554–774] | 212 [156–263] | 24.8 |
| rB (규칙 B) | 579 [443–735] | 226 [144–304] | 18.3 |
- 회차별 rBC1 − rB: +138, +232, −51, −35 QPS. rBC1이 rB보다 낮은 회차는 4회 중 2회 → 기준에 따라 BC1으로 교체.
- 이번에는 rB가 1, 2회째에 크게 낮았다(461, 443). 1차에서 rBC1에 나타난 것과 같은 급락이 다른 정책에서 나타났으므로, 급락은 규칙이 아니라 측정 시점의 서버 상태로 본다(원인 미확인).
- 세 방식(none, rBC1, all)의 QPS 차이는 회차 간 흔들림보다 작다. 디스크 읽기가 없는 조건이라 읽는 양의 차이가 처리량으로 드러나지 않은 것으로 보인다(추정). 11/16에는 all이 3회 모두 none보다 낮았다(602 대 702).
