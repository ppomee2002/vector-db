# w13-c3: 13주차 C3(동시 실행 상한) 측정 원본과 조건

13주차(11/20~)에 서버(cap-vdb)에서 직접 돌린 C3 측정의 결과 파일, 측정 코드, 조건을 정리했다.
측정은 모두 Milvus 2.6.23, pymilvus 3.0.3, 컬렉션 `junlim/nq_seq`(NQ, 64단어 chunk), 캐시가 따뜻한 상태에서 했다.

- 발표에 쓴 측정: 01(5p 그래프), 02(5p 각주), 05(11p 보조 결과)
- 판정을 내지 못한 측정: 03, 04 (실제 질문). 결과가 나빠서 뺀 것이 아니라, 측정 전에 정한 규칙상 판정할 수 없었다.
- 실패한 측정: failed_* (Milvus가 꺼짐)
- 11p 주 결과(B2, 통합 파이프라인 위 C3 몫)는 재은이 측정했다 → pipeline-design 브랜치 `RESULTS_integ.md`. 여기에는 넣지 않았다.

## 측정 01~04, failed_explore 공통 조건 (code/c3a)
- 요청 1건 = [상한 k 대기] → 검색(설정 A/B/C) → 미리 저장한 PK 목록으로 본문 조회 1회.
- 본문 조회 대상은 세 설정이 모두 같다. 질문마다 설정 A의 top-10과 같은 문서의 앞뒤 1조각을 미리 저장했다(질문당 평균 27.3개, 실제 질문만 쓰면 24.75개). 이 사전 검색은 측정 시간에 넣지 않았다.
- 동시 요청 64, 예열 5초 + 측정 20초. 상한 k는 6 / 8 / 12 / 16.
- 질문 집합
  - 01, 02, failed_explore: query_vecs 103,452개(실제 NQ 질문 3,452개 + 가짜 질문 100,000개)에서 고정 시드로 10,000개를 뽑았다. 가짜 질문은 말뭉치 chunk에서 연속 12단어를 잘라 같은 모델로 임베딩한 것이다. 그래서 **질문의 약 97%가 문서 조각**이다. 이 결과를 "실제 RAG 질문 기준"이라고 쓰면 안 된다.
  - 03, 04: 실제 NQ 질문 3,452개만 썼다(`QSET=real`). 구간마다 약 1.2만 요청이라 같은 질문이 3~4번 반복된다. Milvus 결과 캐시 여부는 확인하지 않았다.
- 탐색 세션: 설정 3 × k 4 × 3회 = 36구간. 회차마다 순서를 돌렸다.

## 02 확인 세션 — 5p 각주
- 01과 다른 시간대에 다시 쟀다. 측정 전에 20분 연속 다른 작업이 없는지 확인하고 자동으로 시작했다(wait_run_pf.sh). 측정 중 다른 계정의 새 프로세스는 없었다.
- 순서: 기준 설정(A, k=8) → 비교용 k vs k=12를 4회(설정 순서는 회차마다 돌리고 두 k의 순서는 회차마다 뒤집음) → 기준 설정.
- 판정 규칙(측정 전 고정, analyze_c3a.py 맨 위): ① 4회 모두 비교용 k의 QPS가 높음 ② QPS 평균 차이가 기준 설정을 다시 잰 차이보다 큼 ③ p99 평균 차이 조건. 이 판정은 새 방식을 시도할지 정하는 내부 기준이며 통계적 입증이 아니다.
- 결과 (`summary_confirm_nq.md`)
  - 기준 설정 A k=8: 처음 587 QPS → 끝 393 QPS. 11분 사이 33% 떨어졌고 원인은 확인하지 못했다.
  - A(8 vs 12): 확인 안 됨 (3/4, +8%)
  - B(6 vs 12): 진행 (4/4, +57%, p99도 낮음)
  - C(8 vs 12): 확인 안 됨 (4/4, +35%이지만 기준 설정 차이 194 QPS보다 작음)
  - Milvus CPU는 모든 구간 6.5~7.1코어로 k와 관계없이 거의 같았다.
- 같은 결과 폴더를 썼기 때문에 01의 `c3a_explore.log`, `results_c3a_seq*.csv`가 함께 들어 있다(01과 같은 파일, md5 같음).

## 04 실제 질문 재측정 — 판정 불가
- 03이 오염돼서, 오염을 걸러 내는 규칙을 먼저 정한 뒤 같은 측정을 다시 했다(`code/c3a/judge_c3a_real2.py`, 측정 전 고정).
  - 기준 설정(A, k=8)을 1회차 앞과 각 회차 뒤에 모두 4번 쟀다.
  - 세션이 유효하려면 다음을 모두 만족해야 한다. V1 다른 계정 python 작업 없음 / V2 fork 실패 없음 / V3 회차 앞뒤 기준 설정 차이 15% 이하 / V4 36구간, 오류 0.
  - 15%라는 값은 강한 근거가 없다. 01의 기준 설정 3회 범위(5.4%)와 확인하려는 k=12 손해(약 30%) 사이에서 정했다.
- 결과 (`summary_real2_judge_nq.md`): **판정 불가.** 다른 계정 작업과 fork 실패는 없었지만, 기준 설정이 490 → 444 → 377 → 491 QPS로 바뀌어 2회차(15.2%)와 3회차(23.3%)에서 V3을 넘었다. 15.2%는 기준을 조금 넘은 값이지만, 결과를 본 뒤 기준을 바꾸지 않았다.
- 서버 tgz에는 측정 도중에 판정 코드를 돌려 만든 summary_real2_judge_nq.md(27구간 시점)가 들어 있었다. 여기에는 측정이 끝난 뒤 PC에서 다시 만든 최종 판(36구간)을 넣었다.

## 이 폴더를 만들면서 한 처리
- tgz 안의 `fixed_nq.npz`(질문별 PK 목록, 1~3MB 바이너리)와 `selftest/`(mock 점검 결과)는 넣지 않았다. 넣을 수는 있지만 넣지 않은 것이며, 원본은 서버와 PC의 tgz에 있다.
- 로그와 스크립트 안의 관리자 스위치 주소와 서버 주소를 `<switch-host>`, `<server>`로 바꿨다. 그래서 code/ 안의 .sh 파일은 그대로 실행되지 않는다. 실행하려면 SW_CMD를 지정해야 한다.
- 로그 안의 다른 계정 프로세스 줄은 실행 파일 이름만 남기고 명령 인자를 지웠다. 측정 판정에 쓰는 정보(다른 계정 python 작업이 생겼는지, OVERLAP 시각)는 그대로 남겼다.
- 그 밖의 결과 값은 바꾸지 않았다.
