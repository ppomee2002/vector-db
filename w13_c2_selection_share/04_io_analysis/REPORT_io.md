- 2026-11-22, `/workspace/jaeeun/sel_fetch_io/`. 기존 로그와 결과만으로 분석했다 (새 실측 없음, 공유 자원 사용 없음).
- 수치 표시: **[실측]** = 기존 실험에서 실제로 잰 값, **[계산]** = 기존 로그(선택된 chunk ID, 오프셋)로 센 블록·요청 수와 이를 바탕으로 한 환산.
- 비교: 같은 질문, 같은 Top-100, B=20, 같은 Rerank 점수, A1은 v2 dev 값(maxlog, α=0.3), BC1과 담는 순서는 c2x 고정 규칙, 예산은 GPT-2 15·20 chunk 분량, 저장 방식은 기여 C1(4KB 블록).
- 주 결과는 c2x test(NQ train 2,000개), 참고로 dev(NQ test 2,254개). 스크립트: `scripts/io_analysis.py`, 결과: `results/`

## 0단계: 상한과 전제
### (a) 상한 [실측 조합]
| 항목 | 값 | 출처 |
|---|---|---|
| B=20 최초 Fetch (O_DIRECT, cold) | 1.60ms | c2x 실험 3 ④ [실측] |
| C2 추가 Fetch (재사용 있음) | 0.16ms | c2x 실험 3 ⑤ (B10+BC1, 예산 20) [실측]. **B20+BC1 조합은 재지 않았음** |
| 모든 물리 I/O를 없앨 때 줄어드는 최대 지연 | **약 1.76ms** | 위 둘의 합 [계산] |
| 비교 기준 | A/A 0.39ms, 경로 전체 36.7ms (임베딩·ANN 제외; 포함하면 약 46ms) | [실측] |
- 1.76ms > 0.39ms이므로 판정 기준상 세부 분석을 진행했다. 다만 경로의 3.8~4.8%에 불과하다.

### (b) 중복 방지
- A1과 Top-B의 최초 Fetch cold 차이는 v2 4-2단계 실측을 인용한다: \|S\|=20에서 A1 −1.07ms (전체), Fetch 구간 −1.55ms [실측, v2]. 이번에는 다시 재지 않았다.
- c2x 실험 3 단가로 환산하면 최초 Fetch는 요청당 0.097ms, 블록당 0.086ms다 (회귀) [계산]. 이 단가로 A1의 요청 −2.6개를 환산하면 −0.25ms다. v2 실측(−1.55ms)과 약 6배 차이가 나는데, 두 측정은 날짜, 디코딩 처리, 질문 집합이 다르다. **둘 중 어느 쪽이 맞는지는 기존 로그로 판단할 수 없다** (아래 "부족한 것" 참고).

### (c) 블록 재사용 확인 (코드)
- c2x 실험 3(`c2x_exp3.py`)은 최초 Fetch에서 읽은 블록을 **앱 버퍼(`cache` 딕셔너리 → mmap 버퍼 위치)에 들고 있다가**, 추가 Fetch에서는 `k not in cache`인 블록만 O_DIRECT로 읽었다. 따라서 "추가 블록 0.23개"는 **(1) 앱 버퍼를 실제로 재사용해서 읽지 않은 것을 잰 값**이다 [실측].
- c2x 실험 2의 `blocks_extra`는 블록 집합 차이로 센 **(2) 계산값**이다.
- 실제 시스템: Milvus는 C2 추가 Fetch를 별도 query 호출로 보내고, 본문 필드는 mmap(page cache)에 둔다 (팀원 `load_big.py`). 그래서 page cache가 따뜻하면 재사용과 비슷하게 동작할 것으로 **추정**한다. cold나 reclaim 상황에서 같은 페이지를 다시 읽는지는 **미확인**이다. 아래 표는 "재사용 있음"과 "재사용 없음(블록을 다시 읽음)"을 나란히 계산했다.

## 2단계: 기여 C1 배치에서 블록 중복 [계산, test]
| 항목 | Top-B | A1 |
|---|---|---|
| 최초 후보 중 다른 후보와 블록을 공유하는 비율 | 43.8% | **56.0%** |
| 이웃이 부모 chunk와 같은 4KB 블록에 걸치는 비율 | 100% | 100% |
| 최초 Fetch 블록 → 요청 (묶어 읽기로 합쳐짐) | 16.2 → 12.2 (1.33블록/요청) | 14.2 → 9.6 (1.48블록/요청) |
- **차이의 출처:** A1은 Top-B 밖 후보 6개를 "점수가 높은 문서"에서 끌어온다. 이 후보들은 이미 고른 chunk와 같은 문서, 문서 순 배치에서는 바로 옆에 있다. 그래서 블록을 공유하고 붙은 블록으로 합쳐져서 요청 수가 줄어든다.
- 이웃(±1)은 chunk 평균 397바이트라서 항상 부모와 같은 블록에 걸친다. 그래서 재사용만 하면 C2 이웃의 추가 I/O는 거의 0이다 (남는 0.2블록은 블록 경계를 넘는 부분). 이 성질은 Top-B와 A1에 똑같이 적용되므로 둘의 차이를 만들지 않는다.

## 3단계: IOPS 제한 처리량 상한 [계산만, 실측 아님]
상한 = IOPS 제한 / 질문당 읽기 요청 수 (test).
| 예산·재사용 | 방식 | 요청/질문 | IOPS 1,000 | 3,000 | 10,000 | A1 증가율 |
|---|---|---|---|---|---|---|
| 15, 있음 | Top-B / A1 | 12.40 / 9.80 | 81 / 102 QPS | 242 / 306 | 806 / 1,021 | **+26.6%** |
| 15, 없음 | Top-B / A1 | 14.28 / 11.69 | 70 / 86 | 210 / 257 | 700 / 856 | **+22.2%** |

- 4KB 블록 단위로 IOPS를 센다고 가정하면 증가율은 +14% (재사용 있음) / +10.0~11.8% (없음)이다. 판정선(10%)에 거의 걸린다.
- **현실 점검 [계산]:**
  - B=20 Rerank는 34.9ms [실측]라서 A2 GPU 1장 직렬 처리량은 약 29 QPS다. 이때 필요한 IOPS는 Top-B 약 360, A1 약 280이다. 따라서 **IOPS 제한이 약 360보다 낮을 때만 저장소가 병목이 되고 A1의 이점이 처리량으로 나타난다.**
  - C3 기록(`05_캐시비운직후`): Milvus 경로에서 reclaim 직후 디바이스 읽기는 약 228 IOPS (20.3MB/s)였다. 3,000·1,000 제한은 이보다 높아서 걸리지 않았다 [실측, 참고만]. 경로(Milvus 페이지 읽기)가 달라서 우리 요청 수와 직접 비교할 수는 없다.
