# PLAN_a1io — A1의 실제 I/O 효과 최종 검증 (결과 보기 전에 고정, 2026-11-22)

## 공통
- 질문: c2x test 2,000개(주), c2x dev 2,254개(참고, 0단계만). Top-100과 Rerank 점수는 c2x·v2 것을 재사용. GPU·Milvus는 쓰지 않는다.
- 방식: Top-B(B=20)+BC1, A1(B=20, maxlog, α=0.3)+BC1. BC1 규칙(`pf3_rules.py`), 담는 순서, 토큰 예산(GPT-2 86토큰 × 15·20)은 c2x 고정 규칙 그대로. 참고용으로 "최초 Fetch만(S 20개, C2 없음)"도 함께 계산·측정한다 (v2와 c2x 불일치 정리용).
- 읽기 집합 = 최초 후보 S ∪ 예산 안에 담긴 C2 이웃. 4KB 블록으로 바꾸고, 붙은 블록은 한 번의 요청(extent)으로 읽는다. 최초 Fetch와 이웃을 **한 번에 읽는다** (재사용 문제 없음).
- 배치 확인 (읽기만): 지현 님 `/workspace/jihyeon/c1_w13/store`의 doc 배치는 오프셋이 내 `chunk_store_seq.bin`과 100만 개 모두 같다 → **seq = doc** (같은 배치). rand는 무작위 순열(`default_rng(1)`). 세 파일 모두 같은 chunks.jsonl에서 만들었고 본문 표본 2,000개가 일치한다.

## 0단계 판정 (오프라인 계산)
- 기대: seq·doc에서 A1 요청 약 −21%, rand에서는 차이가 거의 없음.
- **rand에서 A1의 요청 감소가 5% 이상이면** "문서 순 배치 의존"이 성립하지 않는다 → 원인을 분석해서 보고하고 **1단계는 하지 않고 멈춘다.**

## 1단계 (파일 저장소, O_DIRECT, seq 배치)
- 동시 요청 N = 1, 4, 16, 64 (Python 스레드, 스레드마다 정렬된 버퍼, os.preadv). Fetch 단계만 측정한다.
- 실행 단위(run) = (방식 ∈ {Top-B, A1, Top-B 재측정(A/A)}) × (예산 ∈ {15, 20, S만}) × N, 질문 2,000개. 시작 전에 warmup 1회(버림). 3회 반복하고 회차마다 실행 순서를 섞는다 (seed = 회차 번호).
- 측정: run 전후 `/proc/diskstats` loop1 차이 (읽기 횟수, 바이트) vs 앱 요청 수·바이트, 질문당 지연 p50/p99, QPS, A1 선별 계산 시간 (오프라인 함수 시간).
- A/A 잡음 = |Top-B − Top-B 재측정|의 3회 범위. 차이 판단은 3회 모두 같은 방향이고 A/A 범위를 넘을 때만 "차이 있음"으로 본다.

## 1단계 판정 (고정)
1. 장치 읽기 횟수 차이 < 10% → 종료 ("오프라인 계산의 이점이 실제 장치 I/O로 나타나지 않음").
2. 모든 N에서 지연·처리량 차이가 A/A 잡음 안 → 종료 ("장치 I/O는 줄지만 성능 차이로 나타나지 않음").
3. Fetch 단계 최대 처리량 ≥ Rerank 처리량(약 29 QPS)의 10배(290 QPS) → "이 하드웨어와 Reranker 조건에서는 I/O가 병목이 될 수 없음"을 명시한다.
4. 1~3을 모두 통과할 때만(1·2에서 종료되지 않고, 3에 해당하지 않을 때) "Milvus cold 경로와 IOPS 제한 조건에서 검증할 가치 있음"으로 판정하고, 그 실험은 제안만 한다.
- 품질은 새로 계산하지 않고 REPORT_io 값(−0.45 / −0.25%p, CI가 0 포함)을 인용한다.
