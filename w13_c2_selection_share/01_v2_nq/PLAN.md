## 0. 용어
| 용어 | 정의 |
|---|---|
| 후보 | ANN Top-100 (Milvus `jaeeun.nq1m_sel`, HNSW ef=256) |
| 기준 Top-10 | Top-100 전체를 cross-encoder(ms-marco-MiniLM-L-6-v2, max_len 256)로 리랭킹한 상위 10개 |
| 선별 집합 S | 본문을 읽기 전에 고른 후보 집합. S만 Fetch하고 S만 Rerank하며, 최종 Context는 S의 Rerank 상위 10개 |
| **C1** | 문서 순 배치(chunk_id = (doc_idx, chunk_idx) 순서, 0단계에서 확인함) + 4KB 블록 단위 묶어 읽기. 블록 = ⌊offset/4096⌋ … ⌊(offset+len−1)/4096⌋. 붙어 있는 블록들은 한 번의 I/O(extent)로 읽는다. 저장 파일은 `chunk_store_seq.bin` (기존 sel_fetch, 읽기 전용) |
| 개별 읽기 | chunk마다 따로 pread (지난주 방식). 비교용으로만 쓴다 |
| C2-규칙C1 | 팀원 C2 브랜치의 "1위 결과의 이웃" 규칙. 기여 C1과 다르다. 이번 범위에서는 쓰지 않는다 |

## 1. 지표 (우선순위 순)
- **품질 (주 지표):** nDCG@10 (qrels 기준, 최종 Context 순서), 정답 포함률 = 최종 Context 10개 안에 정답 chunk가 있는 질문 비율 (Hit@10)
- 품질 (보조): 기준 Top-10 보존율 = |최종 Context ∩ 기준 Top-10| / 10. 정답 라벨이 없는 (A) 집합에서는 이것만 쓴다
- **비용 (주 지표, C1 기준):** 질문당 읽은 4KB 블록 수, I/O 횟수(extent 수), 읽은 바이트 (= 블록 수 × 4096)
- 비용 (보조): Fetch한 chunk 수 (= Rerank 대상 수 |S|), 선별 계산 시간 (ms/질문)
- 지연시간 (4-2단계): 구간별 시간 (임베딩 / ANN / 선별 / Fetch / Rerank / 기타), end-to-end p50/p95/p99

|---|---|---|

| c. 비용 구성 | 질문당 지연시간에서 Fetch와 Rerank의 비율. 선별의 이득이 "Rerank 대상 수 감소"와 "C1 블록 수 감소" 중 어디서 오나 | Rerank가 지배적이다 (5.3 q/s → 후보 100개에 약 190ms, Fetch는 수 ms) |
| c'. C1 공짜 후보 | Top-B가 읽는 C1 블록 안에 이미 들어 있는 다른 Top-100 후보가 몇 개이고, 그중 기준 Top-10이 몇 개인가 | 같은 문서의 인접 chunk가 많으면 블록 예산을 늘리지 않고도 Rerank 대상을 늘릴 수 있다 (가설 H3) |
| 놓친 chunk 특징 | Top-B와 M1이 놓친 기준 Top-10의 ANN 순위 분포, 이미 고른 문서의 다른 chunk인 비율, 인접(±1, ±2) chunk인 비율 | 상당 부분이 이미 고른 문서 안에 있다 |
| d. 지난주 지연시간 | 로그로 원인 후보(선별 오버헤드, 순서 효과, 캐시, Fetch 비중)를 판단할 수 있나 | Fetch만 측정해서 구간 분해는 불가능하다 → 4-2단계로 넘긴다 |
| e. 로지스틱 2~3 피처 | ANN 순위, 점수 격차, 같은 문서 후보 수로 M1-noPos가 얼마나 재현되나 | M1-noPos 이득의 대부분은 "같은 문서 후보 수"에서 나온다 |

- c의 수치는 기존 로그(Rerank 처리량, Milvus 단건 검색, pread Fetch)를 쓴다. 로그에 없는 "Rerank 시간 vs 후보 수"와 "C1 Fetch 시간"은 GPU0에서 짧은 마이크로벤치(질문 200개, 1회)로 **예비** 측정하고, 정식 측정은 4-2단계에서 한다.
- 지난주와 같은 조건의 재실행은 하지 않는다. M1-noPos 예측값은 저장돼 있지 않아서 같은 코드와 seed로 복원한다 (정의상 같은 결과이고 새 실험이 아님).

### 수정된 Go/No-go (결과를 보기 전에 고정)
- **G1 (사전 정보 상한):** dev에서 같은 C1 블록 예산으로 M1이 Top-B보다 nDCG@10을 +0.005 이상, 또는 Hit@10을 +1%p 이상 올리는 예산 구간이 있나 (B 동등 범위 10~30 기준)
- **G2 (품질 민감도):** 보존율 차이가 nDCG/Hit 차이로 이어지나 (M1과 Top-B의 nDCG 차이의 95% CI가 0을 포함하지 않는가)
- **G3 (비용 구성):** Fetch(C1)가 Fetch+Rerank 시간의 10% 이상인가
- 판단:
  - G1과 G2를 모두 만족 → 2~4단계에서 학습 없는 선별 방법을 비교한다 (블록 예산 기준)
  - G1 또는 G2를 만족하지 못함 → 선별 방법 비교는 최소화한다 (Top-B 대비 1~2개만). 방향을 "Top-B로 충분한가 / B를 얼마나 줄일 수 있나 (Rerank 비용 절감)"로 바꾼다
  - G3를 만족하지 못함 → 이득의 출처를 "Rerank 대상 수"로 보고하고, C1 블록 감소는 보조 지표로만 쓴다
  - 어느 경우든 4-2단계는 실행한다

## 4. 4단계 (오프라인 비교)
### 4.1 비교 대상 (고정)
Top-B (B = 5, 10, 15, 20, 30, 40, 50, 70, 100), M1-noPos (dev 학습), 로지스틱 2~3 피처 (dev 학습), Random-deep 대조군 (Top-(B−x) + 순위 [B, 100)에서 무작위 x개, x = ⌈0.2B⌉, seed 고정), 3단계에서 고른 방법 2~3개. BM25는 없어서 Hybrid RRF는 제외한다.
### 4.2 비교 방식
- x축 = 질문당 평균 C1 블록 수 (보조로 |S|), y축 = nDCG@10, Hit@10 (보조로 보존율). 전체 질문과 headroom 질문(기준 Top-10 중 1개 이상이 ANN 순위 ≥ B0 = 20인 질문, dev에서 정의)을 따로 그린다.
- "낫다"의 정의: test에서 같은 블록 예산(Top-B 곡선을 블록 수에 대해 선형 보간)일 때, nDCG@10 차이의 질문 단위 paired bootstrap(2,000회, seed 0) 95% CI 하한이 0보다 크다.
- 모든 방식은 같은 C1 읽기 방식으로 비용을 센다.

### 4.4 채택 규칙 (5단계, 고정)
- 차이의 95% CI가 0을 포함하거나 nDCG@10 차이가 0.01 미만이거나 Hit@10 차이가 1%p 미만이면, 더 단순하고 비용이 낮은 방식을 채택한다. 단순한 정도는 학습 불필요 > 소수 dev 튜닝 > Log/학습, 그다음 선별 오버헤드가 작은 순서로 본다.
- test (B)에서 효과가 유지되고 (A)에서 보존율 방향이 같아야 채택한다.

## 5. 4-2단계 (End-to-end, 측정 전에 고정)
- 범위: 질문 텍스트 → MiniLM 임베딩 (GPU0) → Milvus ANN Top-100 (ef=256) → 선별 → C1 Fetch (O_DIRECT, 4KB, 붙은 블록은 한 번에 preadv) → Rerank (GPU0, 배치 = |S|) → 최종 Context 10개 준비 완료. LLM 생성은 제외한다 (모든 방식에서 최종 Context가 10개).
- O_DIRECT는 page cache를 거치지 않아서 root 없이도 파일 Fetch를 항상 디스크에서 읽게 만든다 (팀원 measure3.py 방식). Milvus 쪽 cold(reclaim)는 Milvus 전체에 영향을 주므로 **사용자 승인 후에만** 한다. 실행 직전에 `check_busy.sh` 종료 코드가 0이어야 한다.
- 질문 500개 (dev에서 seed로 추출), warmup 50개는 버린다.
- 균형 순서: 방식 k개를 Latin square 순서로 돌리고, 회차마다 순서를 바꾼다 (3회).
- A/A: Top-B(B=30)를 같은 회차 안에서 두 슬롯으로 독립 측정한다. |A−A'|의 95% CI 상한을 잡음 크기 δ로 둔다.
- **판단 기준 (고정):** 방식 X와 기준 Y의 질문 단위 paired 차이의 평균에 대한 95% bootstrap CI가 0을 포함하거나 |차이| < δ이면 "차이 없음"으로 본다. 결론 (a)는 같은 품질에서 Top-B 대비 p50 감소의 CI가 0 아래이고 |차이| > δ일 때 / (b)는 Fetch 구간은 유의하게 줄었지만 end-to-end 차이가 δ 이하일 때 / (c)는 end-to-end가 유의하게 늘었을 때 내린다.
- 측정 전후로 nvidia-smi와 uptime을 기록하고, 측정 중에는 1초 간격으로 GPU·CPU 상태를 기록한다. 동시 요청 1개가 기본이고, 가능하면 동시 요청 4개 조건을 하나 더 잰다.

### 4.3 방법별 공식과 범위 (11-22 10:15 고정, test 결과 보기 전)
- 공통: |S| = B, B ∈ {10, 15, 20, 30}. 튜닝은 **dev에서 B=20의 중복 제거 nDCG@10을 최대화**하는 값 하나로 정하고, 모든 B에 같은 값을 쓴다. 동점이면 더 단순한 값(작은 α, 큰 c)을 고른다.
- **A1 집중형:** 문서 점수 = agg(문서 안 Top-100 후보의 ANN 점수), agg ∈ {sum, max×log(1+count)}. Top-(B−x)는 ANN 순서로 유지하고, 나머지 x = round(αB)개는 Top-(B−x) 밖 후보 중 (문서 점수, ANN 점수) 사전순으로 고른다. α ∈ {0.2, 0.3, 0.5}. 하이퍼파라미터 2개 (agg, α)
- **A2 다양성형:** ANN 순서로 훑으면서 문서마다 최대 c개만 받고, B개가 안 차면 남은 자리는 ANN 순서로 채운다. c ∈ {1, 2, 3}. 하이퍼파라미터 1개
- **B1 피드백:** 1라운드에서 ANN Top-10을 Rerank한다. 다음 라운드에서는 남은 후보 j를 f_j = (1−β)·ann_j + β·max_{i∈CE 상위 3} cos(v_j, v_i) + γ·[j가 CE 상위 3의 문서와 같은 문서] 로 정렬해서 다음 10개(B=15면 5개)를 고른다. |S|=B가 될 때까지 반복한다. β ∈ {0.3, 0.5, 0.7, 1.0}, γ ∈ {0, 0.05}. 하이퍼파라미터 2개. 비용 = Rerank 호출 (B/10)회 + Fetch (B/10)회 + 선별 계산
- **B2 조기 종료:** B1과 같은 방식(같은 β, γ)으로 10개씩 늘리되, 직전 라운드에서 새로 Rerank한 후보가 현재 Top-10에 하나도 들어가지 못하면 멈춘다. 최대 50개. |S|가 질문마다 달라서 Top-B 곡선과 평균 |S| 기준으로 비교한다
- **Random-deep:** Top-(B−x) + 순위 [B−x, 100)에서 무작위로 x = ⌈0.2B⌉개, seed 0
- **C1 확장 (참고):** Top-B + Top-B가 읽은 블록 안에 완전히 들어 있는 후보. |S|가 늘어나므로 같은 |S|의 Top-B와 비교한다

### 4-2 축소안 (고정)
- 방식: Top-B (B=20, 30), A/A용 Top-30 한 번 더, M1-noPos, 그리고 test에서 가장 좋은 A·B 변형 하나씩 (각 B=20, 30). 질문은 dev에서 고른 300개 + warmup 30개. 질문마다 방식 순서를 Latin square로 바꾼다.
- warm = 같은 질문을 한 번 읽은 뒤 (page cache와 Milvus 캐시가 따뜻함). cold = 파일 Fetch를 O_DIRECT로 해서 page cache를 거치지 않음 (loop dio=1). **Milvus reclaim은 사용자 승인 전이라 하지 않는다** → Milvus 쪽은 warm만 잰다.
- 판단: §5 규칙. δ = A/A 차이의 95% CI 절댓값 상한
