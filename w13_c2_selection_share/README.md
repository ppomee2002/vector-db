# W13: 후보 선별(Selective Fetch) × C2 이웃 — 개인 실험 정리

**한 줄 요약:** 로그 없이 고르는 후보 선별(A1·B1)은 데이터셋(NQ·FiQA), C2 결합, 실제 I/O, 강한 Reranker 중 어느 조건에서도 Top-B를 의미 있게 넘지 못했다. 그래서 파이프라인 기본값은 **Top-B + BC1**로 두고, 선별은 연구용 후보로만 남긴다.

- 기간: 2026-11-22 ~ 11-23. 데이터는 NQ 100만 chunk(64단어, MiniLM 임베딩)가 주이고, FiQA는 v3에서만 썼다.
- **폴더 구성:** 각 실험 폴더에는 REPORT·PLAN과 보고서가 인용하는 주요 그림만 그대로 두었다. 요약 CSV·JSON, 스크립트, 나머지 그림은 각 폴더의 `results.tgz`에 있다. 그 폴더 안에서 `tar xzf results.tgz`로 풀면 원래 경로(`results*/`, `scripts*/`)로 복원된다.
- 모든 수치는 각 폴더의 REPORT에서 그대로 옮겼다. 자세한 설정, CI, 한계는 해당 REPORT를 보면 된다.
- 공유본에서 뺀 파일(npy/npz, pkl, `*_scores.csv`, 5MB 넘는 파일, 로그 등)은 [EXCLUDED_FILES.md](EXCLUDED_FILES.md)에 정리했다. REPORT가 가리키는 파일 중 일부(예: `per_query.csv.gz`, v4 `results/s2/*_scores.csv`)는 원본 폴더에만 있다.

## 선별이 Top-B를 넘지 못한 이유

1. **Top-B가 일찍 포화된다.** NQ·MiniLM에서는 B≈20에서 곡선이 평평해서 위로 올라갈 여지가 0.01 이하였다(v2). FiQA는 B=20이 전체 Rerank의 103.6%였다. |S|를 늘릴수록 오히려 손해였다(v3).
2. **Reranker가 정답에 가까워야 "Rerank 상위 후보 회수"가 품질 이득이 된다.** FiQA에서는 ANN과 Reranker의 순위 불일치가 더 컸다. 하지만 이 불일치는 도메인 부적합에서 나온 것이라 선별 이득으로 이어지지 않았다(v3).
3. **A1이 찾는 후보는 대부분 "같은 문서의 깊은 chunk"다.** NQ에서는 Top-B 밖 기준 Top-10의 52.9%가 Top-20과 같은 문서에 있었다. FiQA에서는 이 비율이 13.0%라서 A1의 재료가 없었다(v3).
4. **같은 |S|에서는 넣는 만큼 빼야 한다.** 강한 Reranker에서는 headroom 질문의 이득이 커졌다(B1@20 test 포함률 14.2→16.8%). 하지만 A1·B1은 Top-B에서 빼는 후보의 가치가 새로 넣는 후보와 비슷해서, 새로 맞힌 질문과 잃은 질문이 거의 같았다. B1@20 test 기준 60 / 64다. 학습한 M1-noPos만 잃는 쪽이 절반 수준이었다(v4).
5. **지연시간 이득은 선별이 아니라 |S| 축소에서 나온다.** Rerank가 경로의 81~85%를 차지했다. Fetch를 줄이는 효과는 A1 기준 약 0.25ms였다(a1io 실측). 같은 효과는 Top-B의 B만 줄여도 얻는다(v2, a1io).

## C2 추가 검증 결과 (c2x, io)

- **BC1 선택 규칙의 가치는 작지만 실재한다.** 독립 test에서 무작위 ±1 이웃(R3) 대비 +0.99%p [0.51, 1.48]이었다. 이득의 대부분은 "±1 이웃을 읽는다"는 사실 자체에서 온다.
- **기존 C2의 큰 개선은 대부분 Context가 늘어난 효과였을 가능성이 높다.** 예산 없이 비교하면 BC1 − none은 +5.55%p다. 같은 토큰을 Rerank 확대로 채우면 같거나 더 좋았다.
- **dev에서 본 "C2 이웃 > Rerank 확대"는 test에서 재현되지 않았다.** F2 − F1은 dev에서 +2.44%p였지만 test에서는 −0.60%p였다(예산 15).
- **비용:** 예산 15에서 F2(B10+BC1)는 F1(B15)보다 −8.3ms였고, 그중 97%가 Rerank 감소였다. 기여 C1 배치에서는 이웃이 대부분 이미 읽은 블록 안에 있어서, 추가 I/O가 0.23블록 수준으로 거의 0이다. 즉 C2 이웃은 "Rerank 비용을 아끼고 품질을 0~1.8%p 정도 내주는 교환"이다.
- **결합 I/O(io):** C2 추가 Fetch 쪽에는 줄일 I/O가 거의 남아 있지 않다(앱 버퍼를 재사용하면 질문당 0.2요청). 남은 비효율은 버퍼 재사용 여부라는 구현 문제다.

## 최종 판단과 남은 방향

- **기본 경로: Top-B + BC1.** 학습 없는 선별(A1·B1)은 어느 Reranker에서도 기본 경로에 넣지 않는다.
- **A1** 검증은 종료한다. "문서 순 배치에서 읽기 요청을 약 21% 줄이는 선택지"로 기록만 해 둔다.
- **통합 2차 Reranker(v4 권장):** 기본값은 MiniLM이고, B를 늘리는 쪽(B=20~30)이다. 같은 약 70ms라면 MiniLM Top-100(포함률 0.835)이 m3 Top-10(0.779)보다 낫다. m3는 Rerank 지연 150ms 이상을 감당할 수 있을 때만 쓴다.
- **남은 방향 (실행하지 않음):**
  - 학습한 선별(M1-noPos)은 m3 조건에서 더 나았다(test 포함률 +1.3%p, CI > 0, 판정 대상 아님). "무엇을 빼고 넣을지"를 고르는 신호는 존재한다는 뜻이다. 다만 로그가 필요하다.
  - 질문별로 B와 이웃 수를 다르게 배분하는 규칙은 아직 근거가 없다. C2 팀 결과에서 "이웃 필요"를 미리 맞히는 AUC가 0.43~0.57이었다. Rerank 단가가 큰 조건에서 먼저 확인하는 것이 순서다.
  - 저장소가 원격·저IOPS(약 350 IOPS 이하)로 바뀌면 A1의 요청 감소를 다시 검토할 수 있다.
  - Milvus cold 경로, IOPS 제한, 동시 요청 처리량은 공유 자원이 필요해서 재지 않았다.

## 한계

- 데이터셋은 NQ 중심이다(FiQA는 v3만 사용했고, test 648개로 MDE가 약 0.01). chunking은 64단어 고정만 썼다.
- Reranker는 MiniLM과 bge-reranker-v2-m3 두 종류뿐이다.
- 정답 판정은 문자열 포함 또는 qrels 기준이다. LLM 답변 정확도는 보지 않았다.
- A1·B1 하이퍼파라미터는 NQ test 질문(dev)으로 골랐다. 그래서 dev 수치는 A1·B1에 유리할 수 있다. c2x·v4의 test(NQ train 2,000개)는 "Top-100에 정답이 있는 질문"만 남겨서 절대값이 높다.
- 지연시간은 A2 GPU, 단일 요청, 파일 경로(O_DIRECT) 기준이다. A/A 잡음이 커서 1ms 이하 차이의 크기는 신뢰도가 낮다.
- 다중 비교를 보정하지 않았다.
