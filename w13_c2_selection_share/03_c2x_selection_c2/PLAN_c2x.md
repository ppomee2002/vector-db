# PLAN_c2x — 후보 선별 × C2 이웃 결합 (실험 전에 고정, 2026-11-22)

용어: **C2-규칙C1** = C2의 "1위 결과의 이웃" 규칙, **BC1** = C2-규칙B + C2-규칙C1 (팀 채택 규칙), **기여 C1** = 문서 순 배치 + 붙은 4KB 블록 묶어 읽기.

## (a) 데이터 정합성 (`results/prep_check.json`)
- nq_seq(C2, `load_big.py`가 `/workspace/junlim/data_nq/chunks.jsonl`을 pk_seq 순서로 적재)와 nq1m_sel(선별, 같은 chunks.jsonl → `chunk_store_seq.bin`)을 100만 chunk 전부 본문 바이트로 대조했다: 불일치 0, doc_idx 불일치 0, pk_seq는 항등.
- 규칙 A용 flags(`pf3_out/nq_flags.npy`, 100만 개)와 정답 문자열(`pf3_out/nq_gold.jsonl`, 2,255개 질문)은 chunk 번호가 같아서 그대로 쓴다. C2 규칙 코드는 `pf3_rules.py`(md5 2754643f, 팀 저장소와 같음)를 복사해서 쓴다.
- C2의 정답 판정(`analyze_pf3.has_ans`): 같은 문서에서 번호가 이어진 chunk들을 하나의 글로 이어 붙인 뒤 정답 문자열(정규화 후)이 들어 있는지 본다. **이 판정을 주 지표로 그대로 쓴다** (C2 수치와 비교하기 위해). 이어 붙이기는 인접 chunk에 유리하므로, chunk 하나씩만 보는 판정을 민감도 지표로 함께 보고한다.

## (c) 토큰
- GPT-2 BPE 토크나이저(HF `gpt2`)로 100만 chunk의 토큰 수를 미리 계산해서 메타데이터로 둔다 (`results/chunk_tokens_gpt2.npy`).
- 예산 T_N = N × (corpus 평균 chunk 토큰 수, 반올림), N ∈ {10, 15, 20}.
- 채우기: 방식마다 정해진 순서 목록을 앞에서부터 훑으며 누적 토큰 ≤ T_N인 동안 담는다. **처음으로 넘치는 chunk에서 멈춘다** (건너뛰고 더 담지 않음).

## (d) C2 규칙 고정
- BC1의 이웃 선택은 `pf3_rules.select('BC1', R, doc)` 그대로 쓴다. 다른 규칙(none, A, A3, B, C1, C3, all)은 진단용이다. dev에서 더 좋아 보이는 규칙이 있어도 "후보"로만 보고한다.

## (e) 담는 순서 (모든 방식 공통)
1. Rerank 상위 10개를 CE 순서로 먼저 담는다.
2. 그다음 추가 chunk를 담는다.
   - 이웃(BC1, R3, 상한): 부모(이웃을 만든 결과 chunk)의 CE 순위가 높은 것부터, 같은 부모면 앞 조각 다음 뒤 조각. 두 부모의 이웃이면 먼저 나온 쪽에 한 번만 둔다. 배치(읽는 순서)는 부모 바로 옆이다. 정답 판정은 chunk 번호 연속성으로 이어 붙이므로 배치 순서와 무관하다.
   - R1·R2 무작위: 뽑힌 순서.
   - F1 (Rerank 확대): CE 순위 11위, 12위, …
- 예산을 넘는 이웃은 토큰 메타데이터(ID만)로 **Fetch 전에 제외**한다. 그래서 추가 Fetch 비용은 실제로 담긴 chunk에 대해서만 생긴다.

## 실험 1 (예산 없음, C2 원래 조건과 같음)
- 입력: **Rerank Top-10, B=20** (v2에서 채택한 설정: ANN Top-20을 Rerank한 상위 10개). 비교용으로 ANN Top-10(같은 Top-100의 상위 10)과 C2 원래 결과(nq_seq ef=64 Top-10, `pf3_quality_nq.csv`)를 함께 보인다. 내 구현이 맞는지 확인하려고 C2 hits(ef=64)에 내 평가기를 돌려 C2 수치를 재현해 본다.
- 입력 변화: 같은 문서 chunk가 2개 이상인 질문 비율, Top-10 안의 문서 수, 이웃 후보(all 규칙) 수.
- 대조군 (질문마다 BC1과 같은 개수, 후보가 부족하면 가능한 만큼): R1 = Top-100 \ Top-10에서 무작위, R2 = Top-10의 문서들(corpus 전체 chunk) \ Top-10에서 무작위, **R3 = all 규칙의 이웃 후보 안에서 무작위**. seed 0~19 (20개). 질문별로 20개 seed를 평균한 값으로 bootstrap하고, seed별 평균의 범위도 보고한다.
- 상한 U: "이웃이 필요한" 질문(all 규칙으로는 정답이 있고 none으로는 없음)에서만 all 이웃을 읽음 (C2 lazy_need와 같은 개념).
- 곡선: R3를 질문마다 k = 1…14개씩 고른 경우의 정답 포함률 vs 평균 추가 chunk 수에, 각 규칙의 점을 겹쳐 그린다.

## 실험 2 (같은 토큰 예산)
- 예산 N = 10, 15, 20.
- F1(B): B개를 Rerank하고 CE 순서로 채움. B ∈ {10, 15, 20, 30} (B ≥ N인 경우만).
- F2: B=10 Rerank Top-10 + BC1 이웃 (e 순서).
- F2′(B=20): B=20 Rerank Top-10 + BC1 이웃 → **같은 B에서 F1과 비교하는 표**용.
- F3: R1, R2, R3 (B=10 Top-10 + 질문마다 F2와 같은 개수(BC1이 고른 이웃 수, 예산 적용 전), 담는 순서 e), seed 20개.
- F4: 상한 U (B=10).
- **짝 비교 (비용 차이가 있는 조합):** 예산 15에서 F2(B=10) vs F1(B=15), 예산 20에서 F2(B=10) vs F1(B=20). 같은 B 표: B=20에서 F1(B=20) vs F2′(B=20), 예산 15·20.
- 기록 (방식마다 평균): Fetch한 전체 chunk 수 (= B + 담긴 추가 chunk), Rerank chunk 수 (= B), 최종 chunk 수와 토큰 수, C2 추가 Fetch 수, 읽은 블록 수 (첫 Fetch 블록 + 추가 Fetch 중 첫 Fetch에서 읽지 않은 블록).
- 같은 품질의 비용: 품질(정답 포함률) vs 추정 비용 곡선. 추정 비용 = Rerank 1.73ms/후보 + cold C1 0.131ms/블록 (v2 e2e 단가) + 추가 Fetch 호출 고정비 (실험 3 실측으로 대체).

## 실험 3 (기여 C1 저장소 실측, GPU0)
- 조합 (결과 보기 전에 고정): ① B10/none/예산10, ② F1 B15/예산15, ③ F2 B10+BC1/예산15, ④ F1 B20/예산20, ⑤ F2 B10+BC1/예산20, ⑥ ②의 A/A 복제.
- 경로: Top-100 ID(이미 있음) → S_B를 C1(O_DIRECT, 붙은 4KB 블록은 한 번에 preadv)로 첫 Fetch → GPU0 Rerank → 이웃 선택(ID와 토큰 메타데이터만) → 추가 Fetch (첫 Fetch에서 읽은 블록은 메모리에서 재사용, 나머지만 C1로 읽음) → Context 조립. 임베딩·ANN은 모든 방식에 같으므로 제외 (Milvus 사용 안 함).
- test에서 seed로 고른 300개 + warmup 30개, 2회 반복. 질문마다 방식 순서를 순환하고 회차마다 시작점을 바꾼다. p50/p95, 질문 단위 paired bootstrap CI. A/A로 잡음 δ를 잰다.
- 분리: Δ지연 = ΔRerank 구간 + Δ(첫 Fetch + 추가 Fetch) 구간 + Δ기타. 앞의 것을 "Rerank 후보 수 감소 효과", 가운데를 "I/O 읽기 비용 효과"로 보고한다.

## 품질 지표
- 주: 정답 문자열 포함률 (최종 Context, C2 이어 붙이기 판정).
- 민감도 1: chunk 단위 판정 (이어 붙이지 않음). 민감도 2: 정답 별칭 중 하나라도 숫자만으로 되어 있거나 2단어 이하인 질문을 뺀 결과.
- 보조 (dev만): 정답 passage 포함 (passage 단위 중복 제거, 최종 Context가 정답 passage chunk를 하나라도 포함하는 질문 비율)과 passage recall (건드린 정답 passage 수 / 전체 정답 passage 수).
- 새 정보 분석: 추가 chunk가 정답 판정을 바꾼 경우를 (i) Top-10에 정답 문자열이 없었는데 새로 생긴 경우 (새 정보)와 (ii) 이미 정답이 있었고 정답 passage의 나머지를 채운 경우 (dev, passage 기준)로 나눈다.
- 통계: 질문 단위 paired bootstrap 2,000회 (seed 0), 95% CI.

## 결과 해석 (판정 기준 고정)
| 조건 (test 기준) | 판정 |
|---|---|
| BC1 − R3의 CI 하한 > 0, **그리고** 같은 예산에서 BC1(F2) − F1의 CI 하한 > −1%p | 결합 방향에 긍정적 |
| BC1 − R3의 CI가 0 포함 | B+C1 선택 규칙의 추가 가치가 불명확 |
| 실험 1(예산 없음)에서는 BC1 > none인데, 같은 토큰 예산(실험 2)에서는 F2 − F1 또는 F2 − (none으로 같은 예산을 채운 F1 B=N)의 이점이 CI상 사라짐 | 기존 개선은 Context 증가 효과였을 가능성 |
| 실험 3에서 F2의 총지연이 짝 F1보다 유의하게 낮고 (CI 상한 < 0, \|Δ\| > δ), 품질은 비열등 (−1%p 마진) | 실제 결합 효과의 근거 |
| F2가 품질도 낮고 (CI 상한 < 0) 비용도 높음 | 현재 조건에서 결합 이점 없음 |
| 짧은 답을 뺀 민감도 2에서 BC1 − R3 또는 F2 − F1의 이점이 사라짐 | 우연 일치 효과 |
| dev에서 CI 하한 > 0인데 test에서 0을 포함 | 독립 검증 실패 |
- "F2가 F1과 품질이 비슷하다"는 시스템 특성일 뿐이다. 실험 3에서 실제 비용 감소까지 확인될 때만 결합 효과로 쓴다.
- 비용 배분 규칙(B와 이웃 확장의 배분)은 구현하지 않는다. 다른 Reranker, 데이터셋, chunking 실험도 하지 않는다.
