ANN과 Context의 재사용 패턴, 그리고 캐시 분할

벡터 검색(ANN)이 읽는 데이터와 RAG가 컨텍스트로 가져가는 텍스트(Context)가 서로 다르게 재사용되는지, 그리고 그 차이 때문에 하나로 합친 캐시가 불필요한 디스크 I/O를 내는지 확인했다. Qdrant v1.20.0에 접근 기록 패치를 넣어 NQ 질의 3,452개의 실제 접근을 그대로 받아 적고, 같은 기록으로 캐시 정책을 시뮬레이션했다.

2026-11-09 · 109 서버 · NQ 2.68M chunk, 7 segment · HNSW m=16 ef=64 · top-10 · 4KB 페이지

요약

실험 1 확인ANN 탐색과 Context는 다른 데이터를 다르게 쓴다

실험 1 단서 주의재채점(rescoring) 읽기는 Context와 더 닮았다

실험 2 기각분할 캐시는 통합 캐시보다 거의 낫지 않다

그래도 남는 것 여지OPT와의 격차는 크다

무엇을 쟀나

  1. Qdrant의 HNSW 탐색에서 이웃 목록을 읽은 노드와 거리를 계산한 벡터를, segment별 내부 ID로 기록했다. Gridstore payload 읽기도 point offset, page 파일, 바이트 위치, 길이로 기록했다. 동시성 1로 NQ 질의 3,452개를 한 번씩 돌렸다.
  2. 같은 질의는 같은 데이터를 읽는다(순서만 다르다). 그래서 질의별 기록을 이어 붙여 요청 trace를 만든다. natural은 질의 순열 반복(앞 실험과 같은 seed), zipf는 질의 인기도가 α=1.2 또는 0.9인 분포다. 요청 12,000개 중 앞 2,000개는 캐시 워밍업이다.
  3. 모든 접근을 4KB 페이지로 바꿨다. 벡터는 matrix.dat의 실제 위치, Context는 payload page 파일의 실제 위치다. HNSW 이웃 목록은 links 파일 안에서 노드 순서대로 균등하게 놓였다고 근사했다.
  4. 반환된 Context chunk 34,520개 중 34,515개가 같은 질의의 재채점 대상 안에 있었다. 두 기록의 ID 대응이 맞다는 확인이다.
S1 그래프와 원본 벡터가 모두 디스크

기록 그대로. ANN이 질의당 약 12,300 페이지를 읽는다. 순수 디스크 기반 ANN에 해당한다.

S2 양자화 벡터는 RAM, 그래프와 원본은 디스크

탐색은 RAM의 양자화 벡터로 하고, 이웃 목록(질의당 약 530 페이지)과 재채점용 원본 벡터를 디스크에서 읽는다.

S3 그래프와 양자화 벡터는 RAM, 원본만 디스크

Qdrant가 권하는 on-disk 구성이다. 디스크 읽기는 segment별 상위 10개의 재채점(질의당 약 96 페이지)과 Context(약 11 페이지)뿐이다.

실험 1. 같은 chunk를 ANN과 Context가 얼마나 자주 쓰나

질의 3,452개를 한 번씩 돌렸을 때, chunk마다 ANN이 그 벡터를 읽은 질의 수와 Context로 반환된 질의 수를 셌다. 왼쪽은 HNSW 탐색 전체, 오른쪽은 S2·S3에서 디스크로 가는 재채점 읽기다.

왼쪽: 페이지 인기도(질의 3,452개 1회씩). 오른쪽: 페이지를 다시 쓰기까지 걸린 요청 수의 누적 분포(zipf α=1.2 trace). 탐색 페이지는 소수의 hub가 거의 모든 질의에 쓰이는 긴 꼬리를 가진다. Context와 재채점 페이지는 대부분 한 번 쓰이고 끝난다. 오른쪽 곡선의 끝 높이가 재사용되는 접근의 비율이다.

실험 2. 같은 캐시 용량에서 통합 vs 분할

캐시 예산은 시나리오마다 디스크에 있는 데이터(ANN + Context) 전체 페이지의 1~20%다. 요청한 5/10/20%에 작은 예산 두 개를 더했다. 질의당 디스크 I/O는 4KB 페이지 miss 수이고, 읽은 바이트는 그 4,096배라 같은 비율로 움직인다.

정책 다섯 개. 통합 LRU(실제 시스템의 page cache와 Milvus tiered에 가까움), 통합 LFU(접근 횟수를 eviction 뒤에도 유지하는 perfect LFU), 50:50 분할(LRU), 최적 분할(LRU, ANN 몫 0~100%를 1% 간격으로 훑은 사후 최솟값), OPT(Belady + bypass, 미래를 아는 하한)다. LRU 분할 결과는 stack distance로 모든 크기를 정확히 계산했다.

예산 5%에서 ANN 몫을 바꿀 때의 질의당 I/O. 점선은 통합 LRU, 점은 최적 비율이다. 분할 곡선의 바닥이 통합선과 거의 맞닿는다. ANN 몫을 줄이면 I/O가 빠르게 늘어난다.

해석

    주의할 점

    • 최적 분할은 같은 trace로 비율을 고른 사후 상한이다. 실제로 구현할 수 있는 정책의 성능이 아니다. 그 상한도 통합 LRU와 거의 같다는 것이 이번 결과의 요점이다.
    • trace는 질의 3,452개의 재조합이다. natural은 같은 순열을 반복해 LRU에 불리한 순환 패턴이 생긴다. zipf는 질의 인기도를 가정한 합성이다. 실제 사용자 로그가 아니다.
    • HNSW 이웃 목록의 위치는 균등 근사다. 벡터와 Context는 실제 파일 위치다. 동시 요청의 섞임과 OS readahead는 모델에 없다.
    • 재채점 대상은 segment별 정확 점수 상위 10개로 정했다. 실제 양자화 탐색의 후보와는 조금 다를 수 있고, oversampling을 키우면 ANN 쪽 읽기가 늘어 분할 효과는 더 작아진다.
    • Context는 stored(LZ4) 길이로 페이지를 셌다. chunk가 평균 495B라 대부분 4KB 페이지 하나에 들어간다.
